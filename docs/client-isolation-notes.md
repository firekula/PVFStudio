# 客户端 PVF 验证的隔离约束与证据

本文记录 2026-10-24 的只读调查和隔离测试规则，不是客户端加载成功的结论。实际运行、窗口、原包/新包/负例结果见 [客户端验证记录](client-validation-2026-10-24.md)。所有测试副本、服务、状态和原始日志放在本项目忽略的 `build/client-validation/` 下；不得修改旁边的原客户端或服务端工程。

## 保留现有现场

调查时观察到已有服务端从 `../DF/town-test/DFLegacy.Server.exe` 运行，进程 ID 为 47176；该值仅是当时快照，不是之后停止进程的依据。测试不向既有服务发送登录、管理或游戏请求，不重启它，也不更换它正在使用的 PVF。

运行前后记录原始 `DNF.exe`、`ijl15.dll`、客户端/服务端 PVF 与相关配置的摘要，记录既有进程的可执行路径、PID 和启动时间。只停止测试清单中由本次任务创建且路径、启动时间均匹配的进程；不能按进程名批量结束 DNF 或 DFLegacy.Server。

原客户端位于 `G:\Game\DNF_ACT1\DF`。它的 `DNF.exe`、`Script.pvf`、`audio.xml`、`DFighter.ini`、`RS.dll` 和 `Plugin/dnf.str` 等文件已观察为硬链接。测试副本必须复制实际内容，产生独立文件，不能用硬链接、目录联接或可回写原位置的符号链接来节省空间。复制后应核对摘要和独立文件身份。

除资源目录外，还需复制客户端自身的运行时 DLL、`audio.xml`、`DFighter.ini`、`localpackage.lst`、有效 `ijl15.dll` 及独立配置。不要顺手复制源目录的服务端发布目录、账号配置、数据库、历史 netdump、自动输入时间线、备份或大型调试数据库。PVF 用显式选定的基线或导出文件替换到测试副本中的 `Script.pvf`；源文件始终只读。

## 启动与独立账号

直接启动测试副本的 `DNF.exe`，把工作目录设为其所在目录，传入一个完整参数字符串：

```text
99?<隔离入口host>?<隔离入口TCP端口>?<新测试账号>?<新测试凭据>?0?0?0?0?0?0?0?0
```

字段间用 `?` 分隔，因此生成的测试账号和凭据不能包含该字符。只使用隔离服务中新建的临时账号或测试 bootstrap 机制，不从原 `DFLConfig.ini`、`launcher.json` 或真实 state 中复制、展示或复用既有账号凭据。报告保留脱敏的启动形式，原始含凭据命令行不进入 Git。

这条路线由 `../DFLegacy/src/DFLegacy.Launcher/Program.cs:72` 的 `BuildLauncherData`、`:82` 的 `string.Join` 和 `ClientProcessLauncher.cs:11` / `:14` 的工作目录与单参数传递证实。模式 99 的客户端入口 TCP 路径在静态 `0x00892BEF–0x00892C37` 使用启动数据中的 host/port。

不调用原启动器的正常启动流程：`Services/LaunchFlow.cs:21` 会安装 DLL，`:28` 会尝试 `EnsureServerReadyAsync`。即使这些行为对普通用户合理，也不应让本次隔离验证意外安装到源目录或自动拉起默认服务。

## 端口与服务状态隔离

使用独立服务程序副本、独立配置和独立存档目录；所有文件路径明确指向测试根。所有监听地址与对客户端公布的地址均设为 loopback，不继承源配置中的 LAN 地址。仅换成另一个 loopback 地址、沿用原端口不足以隔离，因为既有服务可能监听 `0.0.0.0`。

下表是候选端口布局，不代表已绑定或永远空闲；每次运行前必须检查占用及 Windows 端口保留情况，必要时整体换一组，并把最终值写入运行记录：

| 用途 | 候选隔离地址/端口 |
| --- | --- |
| 入口 TCP | `127.0.0.1:42311` |
| 频道 TCP | `127.0.0.1:47001` |
| 可选附加入口 TCP | `127.0.0.1:48080` |
| 玩法 UDP 主/次 | `127.0.0.1:47002` / `47003` |
| 管理/账号 HTTP | `127.0.0.1:48081` |
| 可选 CharacterDatagram UDP | 独立配置中关闭，或明确使用独立高端口 |

频道 TCP 地址/端口经 `EntranceMetadata.BuildSingleLocalChannel` 下发；生产 `EntranceService.cs:15494–15503` 以 `GameplayDatagram.PrimaryPort` / `SecondaryPort` 构建玩法 UDP 端口。不能误用 `GameProtocolEngine.Handle` 内示例 fallback 的固定 2311。隔离配置须同时修改绑定端口、Channel 的公布地址、Gameplay 的公布地址及其主/次端口。

只读解析最近五份完整游戏 netdump（53788、4336、42952、67288、78036）时，只统计方向、协议与目标端点，未使用或公开 payload。观测均为入口 TCP → 频道 TCP → 两个玩法 UDP，没有 UDP 2311。这支持当前正常链路的端口分工，但不是所有客户端代码路径的证明。运行时仍需检查测试客户端实际连接的端点；不能仅因配置已改便宣称网络已隔离。

频道名也须符合旧协议字段限制：实际发送的 `Channel.Name + " " + ChannelNumber` 必须是严格短于 20 字节的 ASCII 文本。例如 `External PVF 1` 为 14 字节。F 盘导出包的首轮实测曾因测试名 `External PVF Validation 1` 过长，在组装频道信息时失败；缩短新副本配置后已正常进游戏，原 PVF、客户端与现有服务端均无需修改。

还在客户端 `0x0078C4B5` 发现本地 UDP 5063 参数，随后于 `0x0078C4E2` 绑定。它是本地源端口，不是本表的服务端端口；启动前应核对已有 DNF 实例和占用情况，不能为测试停止其他实例或抢占端口。

## 副本配置与输出

Ijl15 从 exe 旁的 `Config.ini` 加载设置，见 `ijl15_config.cpp:133`、`:202`。测试副本至少设 `EnableAutoInput=0`，不复制 `auto-input.json` 等时间线。自动输入 hook 在 `dnf_patches.cpp:1171` 受该开关控制，关闭后不应驱动既有窗口。

通常关闭 `DumpNetwork`；需要证实端点时只在副本中开启，并设置较小的 `DumpNetworkMaxMegabytes`。`DumpNetworkPayloadBytes=0` 表示保留全部载荷，并非关闭载荷；原始日志可能含测试身份或协议数据，只存放在忽略的运行目录，版本控制内只记录端点/计数摘要。

`dnf_patches.h:10` 开启多实例，`:11` 禁止启动时最小化既有窗口。`output_paths.h:8` 开启输出重定向，`output_paths.cpp:243` 创建相对 `Logs/`，`:245` 创建相对 `ScreenShot/`，`:259` 的策略将日志、转储与截图导向工作目录。工作目录因此必须是测试副本，不能依赖调用者当前所在位置。

现有外置字符串表 hook 从副本 exe 旁的 `Plugin/dnf.str` 读取，写出客户端自己使用的字符串表；该文件必须真复制。它不代替原生 PVF 解密及 CRC 检查。此次不得增加任何跳过 PVF CRC、加载错误或完整性检查的补丁来制造通过结果。

## 判据与副作用边界

至少区分有效原包基线、无修改重建、修正版修改包，以及故意损坏目录/条目校验的负例。采用同一副本 exe、DLL、资源、隔离服务与观察时长，避免把网络或资源缺失误判为 PVF 问题。记录客户端实际读到的 PVF 摘要、进程存活/退出、错误日志和达到的可见阶段；到达频道选择、角色选择、城镇或看到修改字段分别属于不同证明强度，不能互相替代。

不能把“没有启动崩溃”当作所有脚本均加载，也不能把离线 CRC 通过当作运行成功。有效负例应证实当前测试客户端仍执行原生 PVF 校验。修正版公式和缺陷背景见 [格式说明](pvf-format.md)，每种实际结果由 [客户端验证记录](client-validation-2026-10-24.md) 负责。

源码审查未发现现有 Ijl15 的注册表写入或全局 AppData 输出；DNF.exe 的直接注册表导入主要是查询。但这个旧程序及依赖 DLL 还含有服务管理等 API 导入，静态导入不证明执行，也不能据此证明不存在任何全局副作用。实际验证应使用当前已知的模式 99 兼容启动路线，不安装驱动、不改变系统/安全设置，并明确记录观察范围；不能武断宣称文件副本就是完整进程沙箱。
