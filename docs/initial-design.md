# PVF Studio 独立编辑器技术方案

归档说明：本文件来自最初的方案调查，其中服务端源码及样本路径相对于旁边的 `../DFLegacy` 仓库。实际实现、使用方式和验证结果以本项目 README 与后续文档为准。

**后续校正：初版将 key 视为不透明值、计划始终保留原 key 的假设错误。** 原生客户端与两份原包的 96,669 个条目现已证明：条目 CRC/key 以最终相对偏移为初值，目录 CRC/key 以 fileCount 为初值。修改或移动条目均需重算相应 CRC 并重新加密。本文相应读写规则已修正；0.1.0 的历史结果及其局限见 [历史验证记录](validation-2026-10-24.md)，新客户端运行结果见 [客户端验证记录](client-validation-2026-10-24.md)。

日期：2026-10-24。用户已选择基于 IntelliJ 平台的独立桌面程序。

本文是本地代码、两份真实 PVF 样本与 JetBrains 官方资料的调查及设计结果，不代表已经交付可运行的编辑器。未修改服务端、客户端或任何原始 PVF。

## 产品目标

用户直接打开 Script.pvf，在一个独立程序中浏览、搜索和修改脚本，查看差异，导出可供服务端使用的新包。无需安装 IDEA、手动解包整个目录或手工处理加密。

首版支持修改现有脚本。新增、删除、重命名条目，以及物品、技能、任务的专用表单，在基础读写与兼容性验证之后增加。

IntelliJ 提供成熟的编辑器、查找、撤销、Diff 和语言支持设施。响应速度仍取决于 PVF 的读取、缓存与索引实现；当前没有性能实测，不能承诺采用平台后自动更快。

### 当前包的结构

- Magic 为 15 字节 `DNF_SCRIPT_PACK`，后随 12 字节目录头，总头长 27 字节。
- 目录头是 little-endian 的 treeLength、treeKey、fileCount。
- 每条目录记录包含 fileNumber、offset、length、key、pathLength 五个 32 位字段，随后是路径原始字节。
- offset 相对于数据区开始处；加密数据按 4 字节补齐。
- 解密为 `ROR32(ciphertext XOR key, 6)`；给定同一个 key，其数学逆变换为 `ROL32(plaintext, 6) XOR key`。
- 两份样本的路径均为已小写 ASCII，没有重复路径或重复 fileNumber；补齐后的数据范围无重叠、无空洞。
- 目录顺序与数据区物理顺序不一定相同。目录末尾也有填充字节，必须单独保留。

抽查 `.lst/.equ/.stk/.skl/.qst/.dgn/.map/.etc/.ani/.atk/.obj/.til/.npc/.str` 后，内容均为文本，包含标签、反引号、注释及换行。两份包均没有 `stringtable.bin` 或 `n_string.lst`。首版针对这类 ACT1 包，不引入新版 PVF 的 token/stringtable 假设；没有全量证明每个条目都是文本。

### 编码处理

路径 reader 使用 CP949，但当前路径都是 ASCII，不能由路径编码推导内容编码。物品中文名有 CP936 的现有代码和真实测试依据，部分脚本的处理代码使用 CP949。

保留原字节；为每个文件记录选定编码与换行。首版提供 CP936/CP949/UTF-8 的预览和手动切换，使用严格解码、编码回读检查。多个编码均可回读时视为有歧义，不声称自动识别成功；不能在保存时以 `?` 替代无法编码的字符。未知二进制内容提供只读十六进制视图。

### 最初回写假设与已确认的校正

最初调查发现 key 同时参与解密，且不等于默认初值为零的普通内容 CRC32 或补齐内容 CRC32。这个观察正确，但当时由此推断 key 是不透明字段，遗漏了 CRC 的非零初值。

两包 `creature/script/creature.lst` 的明文字节相同，SHA-256 同为 `dcb41b5c63d5f50883427883eb09a8a08f13ef2261e29f53353f26586cc21bf1`，key 却分别是 `0xe9e2f76b` 和 `0xdee6df45`。现已确认原因是两包中条目的相对数据偏移不同，CRC seed 也不同；不能将同文异 key 解释成“不是 CRC”。

当前确认的规则是 `entryKey = zlib.crc32(paddedPlaintext, relativeOffset)`，`treeKey = zlib.crc32(paddedPlainTree, fileCount)`，均取低 32 位。客户端加载器在解密后比较 CRC；现有服务端 reader 只解密，不做同等校验，因此 0.1.0 的回读检查漏过了错误。修正版必须对修改条目与被移动的未修改条目重算 CRC/key，并在最终目录更新后重算 treeKey；无修改往返仍要求逐字节相同。新增 fileNumber 语义及其他 PVF 变体仍未确认；客户端实机加载结果必须单独记录。

## 工程结构

建议使用 Kotlin/JVM；纯 JVM 核心与 IntelliJ 平台代码分离，不依赖运行中的服务端，也不在每次读取时启动 .NET 子进程。

| 模块 | 责任 |
| --- | --- |
| `pvf-core` | 格式识别、目录解析、按需解密、保真回写、格式与边界校验；不依赖 IntelliJ |
| `pvf-workspace` | 原包身份、编辑覆盖层、草稿持久化、差异、变更冲突及导出事务 |
| `pvf-language` | lexer、高亮、折叠、标签 schema；后续实现 PSI、补全和引用跳转 |
| `pvf-workbench` | 文件树、编辑标签页、搜索、Diff、诊断和导出操作 |
| `pvf-product` | IntelliJ 独立产品配置、所需 bundled plugins、JBR、启动器与 Windows 安装包 |

PVF 能力可以在 IDEA 的开发宿主中调试，最终随独立产品内置。`runIde` 和 `buildPlugin` 只是开发宿主与插件构建任务，不能将插件 ZIP 当作独立程序交付。

独立产品应固定经过验证的 IntelliJ 开源 release tag 和对应构建工具，裁剪与 PVF 无关的语言插件。具体平台版本、JBR 和构建版本在产品构建原型验证后固定，不追随 master。

## 用户操作与保存语义

1. 打开 PVF：后台读取头部和目录，显示文件树与路径搜索；目录就绪即可浏览。
2. 打开脚本：按需读取和解密，选择文本编码，显示行号、高亮及当前编码。
3. 编辑与 Ctrl+S：保存到独立工作区，记录变更；原包仍是基线。撤销使用 IntelliJ 文档机制，工作区保存用于重启后恢复。
4. 搜索：支持路径与正文搜索。正文在后台流式扫描，支持取消；结果从文件内容或轻量索引获得，不批量打开编辑标签页。
5. 查看变更：以原始内容为基准展示差异、修改文件数、编码和校验错误。
6. 导出 PVF：先保存编辑文档，创建不可变的变更快照，再写入用户选定的新文件。导出过程中继续编辑的内容留待下次导出，不混入正在生成的包。

界面建议：左侧文件树与搜索；中间多标签编辑器；右侧标签帮助和诊断；底部搜索结果与修改清单。后续物品、技能等表单与脚本视图共用同一文档模型，避免两份配置内容失去同步。

工作区 manifest 保存原包路径、大小、修改时间和完整 SHA-256，以及变更文件的原始内容摘要。首次打开不必等待整包摘要完成即可只读浏览，但草稿恢复与导出前必须完成身份校验。检测到源包变化时停止基于旧快照的导出，并要求重新挂载或比较变更。

PVF 虚拟文件使用稳定的“工作区 ID + 原始路径”身份。保存写入覆盖层，并正确发出 VFS 变更通知、更新时间戳和修改计数。需验证搜索范围、文档保存、Diff 与重启恢复；不能只用临时 LightVirtualFile 就假设获得持久工作区。JAR archive VFS 默认只读，不能直接套用其写入行为。

## 性能设计

- 挂载只加载目录和必要元数据；采用 FileChannel 按位置读取条目，避免整包常驻。内存映射仅作为后续基准比较项，需评估 Windows 文件映射的释放与导出影响。
- 文件树按目录展开构造 UI 节点；不用一个 Swing 节点一次性包装每份脚本的内容。
- 解密、文本转换、正文搜索、索引与封包在后台执行，并有进度和取消；UI 线程只处理短操作。
- 内容缓存按总字节数限制，LRU 淘汰；编辑中的文档和覆盖层持久化另行管理，不能因缓存淘汰丢失改动。
- 当前打开文件才创建完整 Document/语法树。ID、名称、路径和引用信息使用轻量索引；正文搜索不依赖全量 PSI。
- 索引缓存绑定原包摘要、覆盖层版本、编码配置和 schema 版本；修改文件后局部失效。索引未完成时仍可浏览和编辑，明确显示搜索是否完整。
- 全文搜索可以不填充内容缓存，避免一次搜索把所有解密文本留在内存。

测量冷启动到目录可用时间、首开脚本延迟、重复打开延迟、全包搜索耗时与取消延迟、堆内存峰值、导出耗时。每次记录样本摘要、机器、平台版本、冷/热缓存和实际结果；目前没有这些实测数据。

## 导出策略与验收

第一阶段只支持修改已有文件：

- 保留 Magic、目录长度、条目数、目录条目顺序、路径原字节、fileNumber 和目录填充；最终目录 CRC/key 按条目数初值重新计算。
- 未修改条目保留明文及原始补齐。内容和相对偏移均不变时保持原密文；条目被移动或内容改变时，按最终偏移重算 CRC/key 并重加密。
- 按原数据区物理顺序布局，长度发生变化时重新计算各 offset、length、treeLength；不能假设目录顺序等于物理顺序。
- 写同一目标目录中的临时文件，完成结构校验和独立回读后，再提交为目标文件。异常或取消不能留下看似成功的目标包；不覆盖源包。
- 拒绝越界、整数溢出、异常路径、重复条目等未支持情况，保留原样本供诊断。

验收顺序：

1. **读格式**：两份真实包的目录数和抽样内容与现有 C#、Python reader 一致；损坏输入能明确失败。
2. **无修改往返**：重新生成的整包与原包逐字节一致，不只是“复制源文件”通过此项。
3. **修改往返**：测试同长、变长、变短、空内容及跨四字节边界的修改，导出后目录及全部条目满足原生带初值 CRC，明文符合预期；未改条目明文及补齐保持不变，只对未移动的未改条目要求密文保持不变。
4. **编码与草稿**：中文、换行和编码歧义能按指定编码保真；重启后可恢复草稿；不可编码内容不会静默损坏。
5. **失败恢复**：测试中断导出、源包被替换、无写权限等情况；原包及既有草稿保持可用。
6. **服务端兼容**：隔离配置加载导出包，核对目标配置实际生效；不替换运行现场的包。
7. **客户端兼容**：以独立测试副本验证加载和目标行为。reader 回读通过不能代替此项。
8. **独立交付**：Windows 安装包自带所需 JBR，不依赖本机安装 IDEA；在干净用户配置下完成上述核心操作。

新增、删除和重命名功能应在 fileNumber 与目录语义验证后扩展。脚本高亮可与核心读写并行开发；标签补全、引用跳转和专用表单在读写闭环通过后分期加入。
