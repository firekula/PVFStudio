# ACT1 PVF 格式与保真读写边界

本文描述 `pvf-core` 已实现的 `DNF_SCRIPT_PACK` 布局。字段和算法以现有服务端 reader 及本地 ACT1 样本为依据，不适用于所有称为 PVF 的文件。

## 整体布局

所有数值采用 little-endian。`uint32` 字段在 JVM 中按无符号值或原始 32 位 bit pattern 处理。

| 文件偏移 | 长度 | 字段 |
| ---: | ---: | --- |
| 0 | 15 | ASCII Magic：`DNF_SCRIPT_PACK` |
| 15 | 4 | 目录加密区字节数 `treeLength` |
| 19 | 4 | 目录 key，原始 32 位模式 |
| 23 | 4 | 目录条目数 `fileCount` |
| 27 | `treeLength` | 加密目录区 |
| `27 + treeLength` | 余下字节 | 数据区，包括条目、间隙及尾部数据 |

总头长为 27 字节。当前实现要求 `treeLength` 为正数、按 4 字节对齐、不超过 256 MiB，且位于文件范围内。空目录可使用正长度的目录填充区；不接受长度为零的目录加密区。

## 目录记录

目录解密后，按顺序读取 `fileCount` 条记录；每条记录布局如下：

| 记录内偏移 | 长度 | 字段 |
| ---: | ---: | --- |
| 0 | 4 | `fileNumber`，无符号文件编号 |
| 4 | 4 | `offset`，相对于数据区开始处的偏移 |
| 8 | 4 | `length`，解密后逻辑内容长度，不含补齐 |
| 12 | 4 | 条目 key，原始 32 位模式 |
| 16 | 4 | `pathLength`，紧随其后的路径字节数 |
| 20 | `pathLength` | 原始路径字节 |

记录之间没有自动补齐。读完记录后的所有目录剩余字节作为不透明尾部保留，包括非零字节。

路径按 MS949/CP949 严格解码，并检查重新编码后能还原原始路径字节。末尾 NUL 仅在生成查询路径时移除；原始路径字节始终保留。查询路径将反斜杠改为正斜杠、移除开头的斜杠，并使用 `Locale.ROOT` 转小写。空路径、内部 NUL、冒号、空片段及 `.`/`..` 片段被拒绝。规范化后出现重复路径或重复 `fileNumber` 时拒绝打开。

`pathLength` 必须为正数、不超过 1 MiB，且位于目录范围内。当前逻辑内容长度不超过 `Integer.MAX_VALUE`；需要返回 Java 字节数组时，四字节补齐后的大小也必须适合数组。目录元数据、逻辑内容和加密补齐长度分别处理，避免长度计算溢出。

## 加密与 key

目录和每个条目的数据分别按 32 位 word 处理：

```text
plainWord  = ROR32(cipherWord XOR key, 6)
cipherWord = ROL32(plainWord, 6) XOR key
paddedLength = (length + 3) & ~3
```

轮转在 32 位范围内进行；word 本身按 little-endian 读写。每个条目使用自己的 key，目录使用头部的目录 key。

原 reader 将 key 命名为 CRC32，但实测它不等于普通明文 CRC32 或补齐明文 CRC32。相同明文在两个已调查样本中可以使用不同 key。当前 writer 将它视为不透明字段，始终保留原 key，不引入推测的 CRC 生成规则。

这可以与只使用该 key 解密的现有 reader 交叉验证。官方客户端是否还检查其他关系，需要单独验证；加密逆变换正确不等于客户端兼容性已得到证明。

## 物理布局与保真规则

目录顺序不一定等于数据区物理顺序。实现保留原目录顺序，另按 `offset`、补齐长度、目录索引排序，得到稳定的物理处理顺序。相同偏移处的零长度条目排在非空条目前面。

打开时校验所有条目均位于数据区内，并拒绝数据范围重叠。允许前导间隙、条目间间隙与最后条目之后的尾部数据，导出时原样复制。零长度条目允许共享偏移，但位于先前非空条目内部的零长度条目也按不支持的重叠布局拒绝。

首版只替换既有条目的字节内容：

- 头部、原始路径、`fileNumber`、key、目录尾部填充保持原样。
- 未修改条目的完整密文和补齐字节直接复制，不重新解密再加密。
- 按原物理顺序处理，保留每段间隙；长度变化后重新计算后续条目的 `offset` 和对应 `length`。
- 路径及条目数量不变，目录加密区长度无需变化。
- 显式提供与原明文完全相同的替换内容时，按未修改条目处理，保留原有非零补齐。
- 修改后的逻辑长度相同时，保留原解密补齐字节；长度变化时生成新的零补齐。
- 新偏移必须可以表示为 uint32；拒绝未知替换路径、归一化后重复的替换路径和不支持的长度。

无修改导出仍重新生成头部和加密目录，并按物理布局复制各条目、间隙和尾部数据。它没有用“直接复制整个源文件”的快捷方式代替重建验证；因此整包逐字节一致能覆盖实际的目录重建路径。

## 源包快照

`PvfArchive` 只保留目录和元数据；内容按位置读取，不无限缓存已解密内容，也不将整个包读成一个常驻字节数组。

当前打开流程包含完整 SHA-256 验证：

1. 打开只读通道，记录文件身份、大小和修改时间，解析头部与目录。
2. 对打开的通道流式计算完整 SHA-256，复查文件属性。
3. 将保留目录重新加密，与当前通道中的头部和目录密文比较，防止旧目录与新数据快照混搭。
4. 通过当前源路径另开通道，再计算完整 SHA-256，并再次检查文件属性。

`verifyUnchanged()` 同样检查身份、大小、修改时间、原通道摘要和当前路径摘要。这样能发现大小相同、修改时间被恢复的内容变化，以及路径被替换的情况。导出在写入前、写入后和最终提交前进行此检查。

因此当前 `info` 的 `open_ms` 包含两次全文件流式摘要和一致性校验，不能作为仅加载目录的耗时。后续 UI 若需要更快出现目录，可拆分“目录就绪”与“身份校验就绪”；身份校验完成前不能恢复到另一份包的草稿或提交导出。

## 临时写入、验证与 no-clobber 提交

导出先克隆并规范化替换内容，形成固定快照。写入同一目标目录中的随机临时文件，写完后 `force(true)`，随后重新打开导出文件并检查：

- 头部、文件数、总长度与所有目录字段；
- 修改条目的解密明文；
- 未修改条目的完整原始密文；
- 目录原始路径及填充、数据区间隙和尾部数据。

只有验证成功并再次确认源包未变后，才将临时文件提交为指定目标。源包、已有目标、已有硬链接或符号链接目标均不会被覆盖。异常或取消时清理本次创建的临时文件。

“使用临时文件”和“原子且不覆盖地提交”是不同的保证。当前提交使用同目录的 `Files.move`，不传 `REPLACE_EXISTING`，要求目标必须不存在；它没有请求 `ATOMIC_MOVE`，因为该选项的规范允许目标存在时由实现决定是否替换。当前实现承诺不覆盖已有目标，不将所有文件系统上的原子重命名能力视为已保证。工作区自己的 manifest 是另一类对象，使用原子替换更新，不会拿该机制覆盖 PVF。

## 线程与取消

读取使用共享只读 `FileChannel` 的按位置操作，不修改共享的 channel position。文档、搜索和导出必须在 UI 线程之外执行。

`FileChannel` 是可中断通道。尤其在 Windows 独立编辑器中，不要对正在使用共享源通道的任务调用 `Thread.interrupt()` 或 `Future.cancel(true)`：中断可能关闭整个 archive 的共享通道。UI 取消应使用显式取消标志并在工作块之间检查，或为可中断任务使用独立短期通道；取消后不能继续依赖已关闭的 archive。

核心在长循环中检查线程中断，以便停止 CLI 或独立任务并清理临时文件；这不改变共享通道不应被 UI 直接中断的约束。

## 验证证据与范围

合成夹具测试应包含目录序与物理序不同、非零填充、零长度和同偏移、跨四字节边界、变长变短、gaps/trailer、坏目录、重复项、源包变化及拒绝覆盖。真实资产验证使用独立 Python 对照器；可选原 C# reader 宿主验证服务端读取路径。

实际结果以每次生成的 `build/validation/.../summary.json` 和逐项报告为准。完整操作命令见 [README](../README.md)。未启动客户端的 reader 验证不能表述为客户端加载通过。
